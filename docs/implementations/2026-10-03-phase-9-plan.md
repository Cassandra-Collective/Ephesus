## 1. Problem / motivation

On 2026-10-02 the Architect planned M9 — Ephesus's own agent engine and a bench that
measures the harness — and asked that nothing be built yet. On 2026-10-03 he set
what the harness should grow into: the feature sets of the two sources on the Stoa
watchlist (ten rows for Odysseus, six for Hermes Agent), with the brand core kept
and the floor made an optional view mode.

Sixteen features do not fit the approved M9, and several run into decisions already
on the record:

| The feature asks for | The record said |
|---|---|
| libraries and bundled services (mail, calendar, search, model serving) | M9 adds no runtime dependency (DD-M9-3's consequence, M9-PLAN §7.4) |
| a conversation as the main surface | the floor is the dominant pane (UI-DESIGN §4), and it is not to be cut on silence (DD-M9-4) |
| tools from outside servers | M9.3's tool registry is closed; a hire inherits no MCP server (ADR-0026) |
| reading the open web | harness egress is GitHub hosts only (THREAT-MODEL §5); the Stoa studies registered, pinned repositories (FR-13.1/13.2) |
| SSH and cloud sandboxes | "SHALL NOT run agents on remote machines over SSH" (SRS §1.2) |
| a phone that pairs over the LAN | "No TCP port is opened" (ADR-0033) |
| a chat bridge on many platforms | one Slack-compatible bridge, as M7b.4, after M9 |
| text-to-speech | the Herald's wiring is deferred indefinitely (M6.9, 2026-08-30) |

A plan that resolved any of those by itself would have decided on the Architect's
behalf. So the work was: map the features onto the record, ask what the record
could not answer, and only then write the plan.

## 3. Implementation approach

**Map first.** Each of the sixteen features was placed against the repository as
it is at `main` @ `75ec37c`: the subsystem whose job it already is, what exists
today, and which recorded decision it meets. The map is PHASE-9-PLAN §2, and every
"today" cell is a repository fact — `App.tsx` opening on the floor tab,
`harbor/bridge.ts` named in the SDD and absent from the tree, a trigger schema that
knows intervals and no calendar time.

**Ask what the record cannot answer.** Eleven decisions went to the Architect
through the questions workflow, in four batches: the shape of the plan, the
dependency rule, the order against M7b and what the window opens on; then web
reach, MCP, execution backends and the phone; then, with a draft and both source
readings in hand, the phone again, speech, and the watchlist tags; and last, with
the finished plan in front of him, the order once more, the one clause of ADR-0040
his first answer had not covered, and the verdict. The answers and the options
rejected are PHASE-9-PLAN §11 and the decision log.

**A decision taken on a wrong number was asked again.** The order question
(DD-M9-10) was put with "about six months" as the cost of putting every feature
before M7b. That figure was quoted before a single package had been written. Summed
package by package it came to about 48 weeks. The plan did not carry the old
answer forward with a footnote: the question was re-asked on the real figure, and
the Architect moved M7b to after M9f (DD-M9-18). PROGRESS is read top to bottom by
a session resuming at the first unchecked box, so the two post-v1 milestones were
moved physically below M7b there, not merely labelled.

Two answers shaped the plan more than the recommendations did. DD-M9-13 chose a
company-wide MCP registry against the recommendation; it is planned as decided,
with its consequence written into the package, the risk register and the note owed
to the threat model, and with the one standing requirement it meets (NFR-17) applied
as written and flagged for the Architect rather than quietly reinterpreted. DD-M9-15
was first answered in the Architect's own words — *no shortcuts, a proper mobile
system* — which could not be planned without knowing what the source he named
actually does; it was asked again after the reading, and became a seventh milestone.

**Read the sources as data.** Two read-only readers studied the two repositories
at their branch heads — Odysseus at `2992bf6`, Hermes Agent at `7533bd2` — and
reported mechanisms with the path each claim came from. Their reports are untrusted
input twice over: the repositories' content, and a model's summary of it. So
PHASE-9-PLAN §3 names the commits, labels the whole section pre-Stoa evidence, and
has every contract package re-read its subject in a governed `/research` cycle
before a design leans on it. Odysseus is AGPL: patterns only, and none of its
constants or text appears in the plan.

**One structure for seven milestones.** M9-PLAN's own shape is reused so that a
session that learned M9 can read this without learning a second format: a contract
package first, packages as *what · Docs · Tests · Risk*, a mutation round with a
control and an adversarial pass on anything gate-shaped, and an exit that quotes
bench rows.

**The order is a safety argument.** M9d (contained execution, the armed gate)
precedes M9e, M9f and M9g because each of those feeds agents content written by
strangers. That is the reasoning that put M8 before M7b, applied again.

## 4. Mathematical / statistical details

None is implemented by this change. One formula appears in the plan, as a statement
of shape for M9c.2 (model fit):

`need(v, n_ctx) = size(v) + n_layers · n_ctx · d_kv · b + overhead`

In words: the memory a model variant `v` needs to serve a context of `n_ctx` tokens
is the size of its file, plus its key-value cache — one entry per layer per token,
`d_kv` elements wide (keys and values together), `b` bytes per element — plus the
runtime's fixed overhead. A variant *fits* when that need is below the available
GPU memory less a declared margin. The constants, the margin and their sources are
owed by M9c.2's own implementation doc; nothing here was computed or measured.

**The estimate is arithmetic, and it is stated in full.** Each package carries a
nominal size in days or weeks. Converted to weeks at five days each and summed per
milestone: M9b 6.6, M9c 6.5, M9d 8.1, M9e 7.3, M9f 8.6, M9g 4.3, M9h 6.8 — 48.2
weeks of packages. Seven exit reviews at about 0.4 weeks add 2.8, giving about 51
weeks in series. M9c needs only M9 and can run beside the main line, which removes
its 6.9 weeks from the critical path: about 44. On the order DD-M9-18 chose, the
path to v1 is M9b, M9d, M9e and M9f with their exit reviews — 7.0 + 8.5 + 7.7 +
9.0 = 32.2 weeks, M9c beside it, 39.1 in series — and M9g and M9h after v1 are
4.7 + 7.2 = 11.9. These are sums of estimates, not measurements, and the plan's §8
says what cuts the other way.

## 5. Design decisions

**A second plan file, not a longer M9-PLAN.** DD-M9-8 kept M9 untouched. Editing
the follow-on milestones into `M9-PLAN.md` would have put approved and newly
drafted text in one file under one status line. `PHASE-9-PLAN.md` treats M9-PLAN as
the phase's first milestone and links to it; M9-PLAN gained a pointer and nothing
else.

**The SRS is amended only where an answer already changed it.** §1.2's two SHALL
NOT lines would have contradicted DD-M9-14 and ADR-0036 the moment the plan was
recorded, and the SRS outranks the SDD for *what*, so they were amended now, dated,
with the old wording kept. The requirement groups for the sixteen features were
**not** written: each milestone's contract package writes its own against a
governed brief. M9's planning drafted FR-15 and FR-16 at plan time; doing the same
for seven milestones would be requirements for designs nobody has made.

**The SDD, TEST-STRATEGY, THREAT-MODEL and UI-DESIGN are untouched** for the same
reason, and for a second one in the threat model's case: a surface's section is
written by the package that creates the surface — ENGINEERING-STANDARDS §6 item 4
(docs are updated in the same PR), as M8.14 wrote THREAT-MODEL §6.8 for the control
surface. *(Corrected 2026-10-11 at review: this cited a THREAT-MODEL rule "since
M8.14" that the threat model does not state.)*

**ADR-0040 was written now; the other ADRs are owed.** The Architect chose an
option whose text said the decision would be recorded as an ADR, and the decision
is complete in itself. The others (the armed gate, backends, the MCP registry,
remote authorisation, the browser surface, the companion and the rest) each need a
design the contract package has not done, and are listed by working title with no
number.

**Repository content does not arm the gate.** NFR-18 says a target repository's
content is untrusted, and the simplest rule would arm on any untrusted read. It
would also arm every coding agent on its first file and end every unattended run in
approvals — the parked-prompt problem M8c spent four packages removing. The plan
arms on content from outside the company and leaves repository content under the
gate classes that already hold what is irreversible. This is a judgment the M9d.0
ADR must defend, and T-INJECT is how it will be checked.

**The harness is the MCP client.** With a company-wide registry, the remaining
question was where the client lives. In the agent process, each agent would need
each server's credentials. In main, a server holds its own and no agent holds any —
the same shape as `eph-recall` going through the hook endpoint.

**Three of the sources' conveniences are not taken.** A standing grant created by a
chat reply, a model that approves low-risk commands on the operator's behalf, and a
sandbox that switches the approval checks off by being a sandbox. Each would be a
decision made where the record says a human decides.

**The browser surface is a remote surface, not a second window.** The source's
dashboard gives a logged-in user full administration, keys and pairing included.
M9f.6 is bound by the same rule as every other remote surface: it converses, reads
and approves inside a policy, and the machine-only acts are refused by name.

**The companion is designed before it is built, and the design is attacked as a
document.** A security protocol written and checked by the same people is the risk;
M8.0's adversarial pass found three bypasses behind forty green tests, and M9h.0
applies that lesson one step earlier.

**Blind means blind at the judging surface.** The label-to-model mapping stays in
main until the verdict is written. It is not secret from an Architect who opens the
log, and the plan says so rather than claiming more.
