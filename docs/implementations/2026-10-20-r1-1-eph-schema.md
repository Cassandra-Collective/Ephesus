## 1. Problem / motivation

**The formats had a design and no type.** R1.0 redesigned every file the harness
persists (SDD-RUST §4). The packages after this one read and write those files:
`eph-fs` seeds the home (R1.2), `eph-git` commits the Agora (R1.3), and `eph-agora`
keeps the registry, the ledger and the book of record (R1.4). SDD-RUST §4.0 rule 6
says a record is validated on read *and before every write*. That needs one typed
model per file, with every rule the shape cannot carry written as code, before any
store exists to call it. Today's build had five id grammars, three time forms, nested
version fields, and two files written without validation (inventory P1 to P7). Each
model here closes those for its file.

**A Rust crate could land with no test entering it.** ENGINEERING-STANDARDS §6 item 7
says no subsystem falls below its coverage floor and no production module lands
untested. For Rust, that half "arrives with `cargo-llvm-cov` floors at R1". Until this
package, nothing failed when a Rust file had no test. The Architect decided the shape on
2026-10-20: one floor per crate, the lowest line coverage of the three CI platforms,
raised only from CI artifacts, never lowered.

**A write needed no exemption.** Planning a test fixture showed that
`std::fs::File::create_new` was missing from `clippy.toml`'s disallowed methods. It
returns a writable `File`, so any crate could write a file through it without the
`fs-write:` exemption that invariant 3 requires. The exemption rule in
`xtask invariants` did not count it as a write either.

## 3. Implementation approach

### 3.1 One read path, one write path, for every document

`Versioned` names a file and its version and holds the rules its shape cannot express.
`parse` reads in four steps, each with its own error:

1. The text, through `json::strict_value`. `serde_json` keeps the last of two equal
   keys. So a second `destructive` rule in `gate-policy.json` would silently loosen the
   first, and a repeated agent id would drop a hire. The strict reader refuses both,
   naming the key and its line.
2. The version, read before the shape, so a file from another build is reported as
   newer or older rather than as unknown fields.
3. The shape, with `deny_unknown_fields` on every struct and every field the SDD row
   lists as required.
4. `validate`.

`render` calls `validate` first, so no caller can produce a file the next read would
refuse. That is the validate-before-write half of rule 6, available to R1.4's store
before the store exists.

Each `validate` refuses with the field's dotted path and a rule a person can act on
(`agents.agent.mason.envGrants: at most 32 grants`). Values that are their own grammar,
such as times, ids, names and references, are newtypes whose `FromStr` is the
validator, so a malformed one never reaches `validate`. A bad one is refused with an
example of a good one.

**Versions.** Six formats changed shape from today's: `config.json`,
`gate-policy.json`, `triggers.json`, `breaker-stops.json`, `registry.json` and
`tasks.json`. They start at version 2, so a TypeScript-era file at the unchanged home
path reads as "an older Ephesus wrote it … no migration". The three whose shape did not
change, `authority.json`, `github-app.json` and `known-targets.json`, keep version 1
and read today's files correctly (Architect, after review).

### 3.2 The log line: typed writer, tolerant reader

`LogKind` is closed, and each kind's events are a closed list. A kind's list is empty
until the phase that builds its subsystem defines it, so the writer cannot emit a line
no reader knows. Only `degradation` (`raised`, `cleared`) is defined in R1.1. Today's
`message` and `memory` kinds are not carried, because no code emits them (P7).

`render_line` validates and prints one compact line. `read_line` never fails. It
returns one of three results:

- an entry;
- an *unknown* line: a newer version, or a well-formed kind or event this build lacks.
  It is kept and counted.
- an *unreadable* line: not JSON, a key written twice, or a kind or event that is
  missing or not text. That is damage, never read as a newer build's line.

Whether an unreadable line is a torn tail or damage in the middle depends on where it
sits in the file, which is the log reader's call (R1.4), not the line's.

A degradation row stores each fact once. Its source is its cause's (`<source>/<slug>
[:<subject>]`). Whether its line raises or clears follows from the row: a row with
`clearedAfter` is a clear. `to_line` takes no event, and `from_line` refuses a line
whose `event` disagrees. One row is kept per cause, not per occurrence. The book of
record gets the first occurrence, every power of ten, and the clear (`earns_log_line`).

### 3.3 Coverage: production lines, per crate, from the syntax tree

`cargo xtask coverage` runs `cargo llvm-cov --workspace --locked --lcov`. It first
deletes the previous report, so a failed run leaves none. It reads the report's line
hits and maps each file to its crate by path. Only files under a crate's `src/` count.

From each such file it removes the lines of every item that compiles only for tests:
`#[cfg(test)]`, `#[cfg(all(.., test, ..))]`, or a test attribute such as `#[test]`, at
any depth of inline modules, impl blocks and traits. Those spans come from `syn`, so a
test helper sitting above production code is excluded correctly, which a cut at the
first `#[cfg(test)]` would get wrong. Two shapes are refused:

- an out-of-line `#[cfg(test)] mod x;`, whose file would be counted as production;
- an item under `#[cfg(not(test))]`, which no test build compiles.

The tally reads the report and the tree in both directions. A production file the
report never names fails if it holds a function body. Such a file is declared by no
`mod`, compiled only on another platform, or holds only generics nothing instantiates.

The check then holds the module's rules 2 to 7:

- no production file no test enters;
- a row for every crate and a crate for every row;
- no regression beyond the tolerance;
- no platform more than the lag above its own recorded figure;
- no measurement taken with a different tool from the floors'.

The floors file's validator holds rule 8: it refuses what only a hand could write.
That is a floor below its own lowest platform figure, a tolerance over 1.00 point, or
rows without three recorded runs per platform.

`emit` prints the measurement of the report the last run left, with the condition it
was taken in: the platform, the tool's version, the tree hash, and the CI run's id,
attempt and commit when the CI variables are set. It refuses a report older than any
member source, because CI caches `target/` and a report can outlive its tree.

`ratchet <dir>` reads every `.json` file under a directory of downloaded artifacts. It
raises the floors only from CI runs of the current tree, three per platform, with each
`(platform, run, attempt)` counted once. It prints the new file, since xtask writes no
file (§5). The developer redirects the output and moves it into place:

```bash
cargo xtask coverage ratchet dl > floors.new && mv floors.new xtask/coverage-floors.json
```

**Seeding a new crate's floor:**

1. Push. The `rust` job fails at the coverage step, by design: the crate has no floor.
2. Rerun it with `gh run rerun <run> --failed` (`gh run rerun <run>` once it is green)
   until each platform has three attempts.
3. After each attempt, download its artifacts with
   `gh run download <run> -p 'rust-coverage-*' -D dl/attempt-<n>`.
4. Ratchet and commit.

The floors file is not part of the tree hash, so that commit is a run of the same tree
and goes green.

## 4. Mathematical / statistical details

**A crate's figure.** For crate *c*, let *P(c)* be the lines the report marks executable
in files under *c*'s `src/`, less the lines of test-only items. Then

> covered(*c*) = |{ *l* ∈ *P(c)* : hits(*l*) > 0 }|, count(*c*) = |*P(c)*|,
> fig(*c*) = ⌊ 10000 · covered / count ⌋ in hundredths of a percent.

Rounding down means a figure never claims more than was measured: 941 of 1004 is
93.72%, not 93.73%. A crate with count 0 has no figure and fails.

**The floor.** Over the corroborating runs *R*, with three per platform *p* ∈ {linux,
macos, windows}:

> rec(*c*, *p*) = min over the *p* runs of fig(*c*), floor′(*c*) = min over *p* of rec(*c*, *p*),
> floor(*c*) ← max(floor(*c*), floor′(*c*)), refused when floor′(*c*) + τ < floor(*c*).

So a floor only rises, and a fall cannot be ratcheted in. Because floor ≥ min over *p*
of rec(*c*, *p*) after every ratchet, a file whose floor sits below its own lowest
platform figure was lowered by hand, and the validator refuses it.

**The check, on platform *p*.** It fails when fig(*c*) + τ < floor(*c*) (regression),
and when fig(*c*) > rec(*c*, *p*) + λ (the record has fallen behind). The lag compares a
platform with its own record because platform-specific code puts one platform above the
cross-platform floor by design. τ = 0.00 and λ = 5.00 points, with their reasons in the
floors file. τ may not exceed 1.00 point: a wider band lowers every floor at once
without touching a row.

**τ was measured, not assumed.** Three `cargo llvm-cov --workspace` runs on win32, one
tree, n = 3: all 24 measured files agreed line for line, a spread of 0.00. With n = 3 a
timing-dependent path the runs happened to take alike cannot be ruled out. No crate has
one yet, and a crate that brings one re-measures (the floors file says so).

**The tree hash.** FNV-1a, 64-bit: *h₀* = 0xcbf29ce484222325, and for each byte *b*,
*h* ← (*h* ⊕ *b*) · 0x100000001b3 mod 2⁶⁴. It runs over the files sorted by path. Each
file contributes its path, a NUL, its text with CRLF turned into LF, and a NUL. The
files are every member's manifest and sources, plus `Cargo.toml`, `Cargo.lock`,
`rust-toolchain.toml` and `.cargo/config.toml`. The NULs keep a path from running into
its text and one file from running into the next. The tests pin the published vectors
for the empty input, `"a"` and `"foobar"`.

**The ladder.** The *n*th occurrence of a degradation is written when *n* = 10ᵏ for some
*k* ≥ 0, computed by multiplying up from 1 with an overflow check, so `u64::MAX` is
handled.

**The time range.** A timestamp is written only for instants from
0000-01-01T00:00:00.000Z (−62 167 219 200 000 ms) to 9999-12-30T22:00:00.000Z
(253 402 207 200 000 ms). The lower bound is the first four-digit year, since a negative
year would render text the strict reader refuses. The upper bound is the last
millisecond `jiff::Timestamp::from_millisecond` accepts: measured, it is 999 ms below
`jiff::Timestamp::MAX`, and a test pins it.

## 5. Design decisions

- **Production lines only.** Counted, `eph-schema`'s inline tests were 915 lines
  against 1004 production lines, and they cover themselves. A production drop would
  show at about half its size: the first measurement read 96.66% with tests and 93.72%
  without. The TypeScript floors measured `src/` without `test/` as well. Rejected:
  counting everything (cargo-llvm-cov's default), and moving tests into `tests.rs`
  files excluded by a filename pattern. That would restructure every file and set a
  convention, where the syntax tree already says which lines are tests.
- **xtask writes no file.** RUST-PLAN §3.2 gives the write exemption to `eph-fs` alone,
  and xtask may claim only `process:`. Widening that would change what `invariants`
  refuses. The two things that must reach disk go to stdout instead: CI redirects
  `emit`, and the developer redirects `ratchet`. A refused ratchet prints nothing to
  stdout, so a redirect cannot capture a half-written file. Once R1.2 builds
  `eph_fs::write_atomic`, xtask could gain a `--write` through it.
- **A crate without a floor fails, so the commit that adds one is red in CI by design.**
  The floor can only be measured after the code is pushed. A pass for "no floor yet"
  would let a crate live without one, and ES §6 item 7 forbids inventing another
  platform's figure. So that commit's coverage step is red, the next commit carries the
  seeded floors, and it is green.
- **The artifact name carries the attempt.** Three runs per platform are three attempts
  of one run, and `upload-artifact@v4` refuses a duplicate name within a run. The
  ratchet counts `(platform, run id, attempt)` once, however many times it was
  downloaded, and refuses two copies of one identity with different figures.
- **FNV-1a over the sources, not git's tree id.** Asking git would need a `git:`
  exemption in xtask (invariant 4), and would see only committed files. A Windows and
  a Linux checkout of one commit must agree, so line endings are normalised.
- **No list of known untested files.** The TypeScript record carries one for its legacy.
  The Rust workspace starts without any, so the rule has no exceptions.
- **The coverage step reruns the suite instrumented, after `test`.** It replaces nothing
  in the approved order, at a cost of about 37 s on this machine for the workspace.
- **Required means required.** Every field an SDD row lists without `?` and today's
  validator requires is required on read: `hire`, the log line's `data`, the task's
  `spec`, `deps`, `review`, `gates` and `artifacts`, the memo list, the registry's
  `capabilities` and `envGrants`, gate-policy's `rules` and a stop's `detail`. A `|null`
  field reads an absent key as null, since serde treats a missing `Option` that way;
  that is the one leniency kept. The first draft defaulted the lists and renamed
  `resultRef`. The fidelity review aligned both with the approved rows, and `profile`
  returned to today's 64 characters.
- **The trait is `Versioned`, as ADR-0041's invariant-9 row and RUST-PLAN §3.1 name it**,
  so a search in the ADR's words finds it.
- **Limits, stated rather than hidden.** The coverage module's doc lists what it cannot
  see: the body of a generic function nothing instantiates, in a file the report does
  name, and code a macro generates. In `eph-schema`, the few lines no test can reach
  are branches that cannot run by construction: a serialised struct is always a JSON
  object, and serialising these types cannot fail. They stay uncovered rather than being
  tested through a contrived seam.

Every survivor was answered rather than counted:

- **Twenty were untested limits** (`eph-schema` round 1). Each cap had a test past its
  limit and none at it: grants (64), domains (32), the spend ceilings, the pacing
  bounds, the hop cap, the id length, task priority and dependencies, and an agent
  retired the instant it was hired. Each now has a test of both sides.
- **Four were equivalent mutants, and three of them were design smells.**
  - `check_version` compared for equality and then with `>`, so `>=` could not be
    told apart; it is one three-way comparison now.
  - `earns_log_line`'s early exit changed no answer; it walks the twenty powers of
    ten a `u64` holds.
  - The JSON reader's own `visit_string` was a method nothing called. serde_json
    hands decoded escapes to `visit_str`, and serde's default forwards there, so it
    is deleted (`eph-schema` round 2).
  - The fourth is a true equivalent and is excluded in `.cargo/mutants.toml` with its
    reason: `visit_unit` returns `Value::Null`, which *is* `Value::default()`.
- **The rest were missing tests:**
  - **`eph-schema`:** a positive `Duration::from_millis`; the reader's own `expecting`
    text; and the reason an older log line gives.
  - **`xtask`:** `points`' epsilon test had a boundary no input could reach, and is an
    exact two-decimal check now. `Real::tool` had no test of its success path, so it is
    restructured and tested against the installed cargo-llvm-cov. `main`'s arms were
    untested, so parsing moved into a pure `parse_args` with every form tested.
- **One is recorded, not killed:** `CargoRunner::coverage` replaced with `Some(1)`. A
  test through the real runner, with the xtask binary standing in for cargo, kills the
  `None`, `Some(0)` and `Some(-1)` mutants. Telling `Some(1)` apart needs a coverage
  step that returns 0. That takes a real instrumented run of a whole workspace, which
  `cargo xtask gate` performs on every invocation (the refutation baseline above, exit
  0). Doing it inside the suite would nest one coverage run inside another, once per
  mutant. The reason is in the test's comment.
